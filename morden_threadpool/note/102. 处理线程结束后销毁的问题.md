### 1. 问题重述：线程“自毁”导致的死锁
**现象：**
在线程池的 `Cached` 模式下，当线程因为长时间闲置需要退出时，如果它在自己的线程函数（`ThreadFunc`）中直接执行 `threads_.erase(tid)`，程序会发生死锁或崩溃。

**根因：**
1. **所有权关系：** `ThreadPool` 使用 `unordered_map` 存储 `unique_ptr<Thread>`。
2. **触发析构：** 当线程在 `ThreadFunc` 内部执行 `erase` 时，会销毁 `unique_ptr`，进而触发 `Thread` 对象的析构函数。
3. **自锁逻辑：** 在 `Thread` 的析构函数中，通常会写 `if(thread_.joinable()) thread_.join();`。
4. **致命冲突：** `join()` 的含义是“等待目标线程结束”。此时，**线程 A 正在执行析构代码，它在等待线程 A 结束**。这种“自己等待自己”的行为会导致永久死锁。

---

### 2. 解决方式：回收队列模式
**核心思路：**
将**“线程逻辑执行完毕”**与**“线程资源回收（join）”**两个动作解耦。线程只负责报备自己已结束，由其他线程（或析构函数）负责真正的回收。

**具体步骤：**
1. **建立报备机制：** 在线程池类中增加一个 `std::vector<int> exitedThreadIds`，专门记录已经跳出循环、准备退出的线程 ID。
2. **线程安全退出：** 线程在 `ThreadFunc` 的最后（`EXIT_HANDLER`），不再删除自己，而是把自己的 ID 放入 `exitedThreadIds`。
3. **延迟回收（核心）：**
   * **析构时回收：** 在线程池析构函数中，利用信号量/条件变量确保所有 `ThreadFunc` 都跑完了，最后统一遍历容器 `join` 所有线程。
   * **动态回收：** 在调用 `createThread` 创建新线程时，顺便检查 `exitedThreadIds` 队列，将里面记录的旧线程从 map 中 `erase` 掉。此时 `erase` 是由“当前线程”操作“旧线程”，不再是“自己操作自己”，因此 `join` 可以正常成功。

---

### 3. 核心逻辑,伪代码

**错误的做法（死锁）：**
```cpp
// 在线程自己的函数里
ThreadFunc() {
   ...
   pool->threads_.erase(myId); // 触发 ~Thread() -> join() -> 自己等自己 -> 死锁！
}
```

**正确的做法（延迟回收）：**
```cpp
// 1. 报备
ThreadFunc() {
   ...
   lock(exitMtx);
   exitedThreadIds.push_back(myId); // 只是登记
   exitCond.notify_all(); 
}

// 2. 由别人回收
cleanThreads() {
   lock(exitMtx);
   for(id : exitedThreadIds) {
      threads_.erase(id); // 这里触发 join，是安全的
   }
}
```

---

### 4. 为什么这样最优雅？
1. **符合资源管理原则：** 谁创建，谁负责回收。线程池创建了线程，就该由线程池的主控逻辑来清理。
2. **保证内存安全：** 避免了使用 `detach()` 可能导致的“孤儿线程”访问已销毁对象的问题。
3. **性能平衡：** 只有在需要扩容或池销毁时才清理，减少了频繁加锁清空的开销。
